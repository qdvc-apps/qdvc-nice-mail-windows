## 2. LLM response

The app is a fairly classic desktop utility: a menubar, a tab strip, per-tab toolbars, sortable/resizable column tables (emoji and phrases), a text preview (signature), a small form (Note to Self), a preferences dialog, and plain-text files in a workspace folder. That shape matters, because it maps almost 1:1 onto traditional Win32 controls. You don't need anything exotic to make it feel at home on Windows.

Here are the realistic options, roughly in the order I'd recommend them.

### 1. C# + WinForms with just the .NET SDK (my top pick)

This is probably the sweet spot for "native feel, light toolchain." You install the .NET SDK (a single installer, no Visual Studio), then use the `dotnet` CLI with VS Code or any editor:

```
dotnet new winforms -n NiceMail
cd NiceMail
dotnet run
dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true
```

WinForms wraps the real Win32 common controls, so the result looks and behaves like a native Windows app. You get proper keyboard navigation, accessibility, and system theming for free. The app's UI concepts map directly. `MenuStrip` gives you the menubar with `&File`-style mnemonics and inline shortcut display. `TabControl` gives you the tabs, with a `ToolStrip` inside each tab page for the per-tab toolbars. A `ListView` in Details mode gives you the emoji/phrase tables with resizable column headers and right-click context menus. `FontDialog` handles the preview-font preference, and `SaveFileDialog` handles the `.eml` export.

The one thing you give up without Visual Studio is the drag-and-drop form designer. For an app this size, laying out controls in code is very manageable, and arguably cleaner.

### 2. Free Pascal + Lazarus

If you'd like a single native `.exe` with no runtime at all, Lazarus is worth a serious look. It's one modest installer that includes the compiler, IDE, and a visual form designer. Its LCL widgets map onto real Win32 controls, so the result feels native. It produces a few-MB standalone executable. It even supports GTK on Linux, so one codebase could theoretically cover both platforms. The trade-off is Object Pascal and a smaller ecosystem.

### 3. Stay in Python, but switch to wxPython

If you want to keep the existing model code, this is the least disruptive route. That includes the workspace/CSV handling, signature assembly, message-ref generation, and `tests_model.py`. wxPython uses genuine Win32 controls on Windows, unlike Tkinter or Qt, which draw their own. You'd rewrite only the `qdvc/gtk3` view layer and package the app with PyInstaller. Downsides: a larger distributable, slower startup, and PyInstaller executables sometimes trip antivirus heuristics. The upside is that Python's `unicodedata` keeps working, which matters more than you might think (see below).

### 4. WinUI 3 / Windows App SDK

This gives the most modern Windows 11 look (Mica, Fluent styling), and it can technically be built with just the `dotnet` CLI. In practice, the tooling is noticeably rougher outside Visual Studio: XAML with no designer, plus packaging and deployment quirks. Its UI idioms also lean toward `NavigationView`/`CommandBar` rather than the menubar-plus-toolbar layout this app uses. I'd consider it only if the "looks like a 2025 Windows app" factor is important to you.

WPF sits between WinForms and WinUI. It's CLI-buildable and flexible, but it doesn't look particularly native by default.

### Porting details worth planning for

**Emoji rendering is the biggest gotcha.** Classic GDI-based controls, which include WinForms' `ListView`, generally draw emoji from Segoe UI Emoji in monochrome, not colour. For an app whose first tab is an emoji picker, that's noticeable. Your options are to accept it, owner-draw the emoji column using DirectWrite (some work), or choose a stack that renders colour emoji natively, such as WinUI 3. It's worth prototyping this first, whichever route you pick.

**Emoji names come from Python's `unicodedata`.** The app derives IDs like `waving_hand_sign` from `unicodedata.name()`, and .NET has no built-in character-name lookup. The simplest fix is a one-off Python script that exports the emoji catalogue (codepoint, ID, name) to a CSV or JSON file you embed in the Windows build. This also guarantees the IDs match, so `favourite_emoji.csv` remains compatible.

**Keep the workspace format identical.** If the CSV and text layout stay the same, the same workspace folder, perhaps synced via OneDrive or similar, could be used by both the Linux GTK version and the Windows version. That's a nice property to preserve. In C#, CSV this simple can be hand-parsed, or you can pull in CsvHelper.

**Preferences** should move from a YAML file to `%APPDATA%\QDVC\NiceMail\`. JSON via the built-in `System.Text.Json` avoids an extra dependency.

**The `.eml` export** is simple plaintext RFC 5322. You can write the headers yourself, or use MimeKit if you'd like something more robust.

**Global Ctrl+C needs care.** In WinForms, a menu item bound to Ctrl+C will intercept the shortcut even when a text box has focus, which would break copy in the Note to Self fields. You'll want to check the focused control and fall through to normal text copying when appropriate.

**Message refs** are trivial: .NET 8+ has `RandomNumberGenerator.GetItems()`, which can draw directly from your unambiguous alphabet.

If you'd like, I can sketch the WinForms skeleton for you, with the main window, tabs, per-tab toolbars, and the ListView-based emoji table, so you can see how closely it tracks the GTK structure.

## 4. LLM response

I've built the WinForms port as a solution with a UI-free model layer, one `TabView` per tab, xUnit tests, and a sample workspace. It needs only the .NET SDK: `dotnet run --project src/NiceMail -- sample-workspace` to try it, or `dotnet test` for the model tests. The ZIP is below.

**Two things you should know first.** I couldn't compile or run it, because this sandbox has no .NET SDK and no network access. I went through the code by hand for compile errors and fixed several, but expect to fix a small error or two on the first build. Also, GitHub blocked me from reading the Python source files, so I rebuilt the behaviour from the README, which is very detailed. The main thing that depends on this is how emoji ids are formed: I assumed snake_case of the Unicode name (`waving_hand_sign`) and `custom_<lowercase hex codepoints>` for pasted emoji. If you open an existing Linux workspace and a favourite goes missing, that assumption is the first thing to check.

**How it matches the GTK layout:**
- **Window structure:** menubar on top, then the tab strip, and each tab has its own toolbar underneath. The Emoji and Phrases tabs have a second toolbar row with a search box that stretches to the full width.
- **Menus and shortcuts:** the menus use &File/&Edit/&View/&Help mnemonics and show their shortcuts. Ctrl+O, Ctrl+C, Ctrl+F, Ctrl+R, F5 and Ctrl+, all work.
- **Ctrl+C inside text boxes:** Edit → Copy checks which control has keyboard focus. If it's a text box with selected text, it copies that text. Otherwise the active tab decides what to copy.
- **Toolbar icons:** these are drawn at runtime from the Windows icon font (Segoe Fluent Icons on Windows 11, MDL2 Assets on Windows 10), so there are no image files and they match the system style.
- **Preferences** are saved as JSON in `%APPDATA%\QDVC\NiceMail\`. They cover toolbar label position, skin tone, the preview font with a Default button, and reopening the last workspace. The app also remembers the Disclaimer, Ref Only and profile choices, the Note to Self address, and the window size.
- **Emoji names:** .NET can't look up Unicode character names the way Python's `unicodedata.name()` does. So `tools/generate_emoji_catalogue.py` builds `emoji.tsv` (1,377 emoji) ahead of time, and the file is embedded in the exe. If you pass it Unicode's official `emoji-data.txt`, it uses the exact emoji properties instead of my built-in table.
- **Note to Self** writes a proper RFC 5322 `.eml` file. Headers with non-ASCII text are encoded correctly, and it switches to base64 if any line is too long.

**Known limitation:** the emoji list shows emoji in black and white, because the standard Windows list control can't draw colour emoji. The characters that get copied are correct and appear in colour wherever you paste them.
